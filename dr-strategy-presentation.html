Part 4 — Failover Process: AWS Site Failure

Failover Process — AWS Site Failure Scenario

1
🚨 FAILURE DETECTED
AWS us-east-1 becomes unavailable. Route53 health checks fail on 3 consecutive checks (30s interval).
2
⚡ AUTOMATED TRIGGER (T+30 seconds)
EventBridge rule fires. Step Functions workflow initiated. PagerDuty alert sent to on-call team.
3
🗄️ DATABASE PROMOTION (T+60 seconds)
On-prem PostgreSQL (Patroni) promoted from replica to writer. AWS DMS reverse task activated. Aurora us-west-2 promoted to writer for AWS-side apps.
4
💻 COMPUTE SCALE-UP (T+2 minutes)
Zerto initiates failover of AWS-primary VMs to on-prem replicas. On-prem K8s scales up (KEDA). Pre-warmed instances absorb traffic.
5
🌐 DNS FAILOVER (T+3 minutes)
Route53 updates weighted records. TTL 30s ensures fast propagation. 100% traffic now routed to on-prem. Global Accelerator anycast updated.
6
✅ FAILOVER COMPLETE (T+5 minutes)
On-prem serving 100% of traffic. All app groups active. Monitoring confirms healthy state. RTO achieved: < 5 minutes.
7
🔄 FAILBACK (Manual, T+hours)
1. Confirm AWS restored (15 min observation).  2. Re-sync data delta.  3. Verify replication lag < RPO.  4. Gradual traffic shift 10%→25%→50%→100%.  5. Post-incident review.
Part 4 — Failback Process

Failback Process — Controlled Return to AWS

Phase 1
VERIFY
Confirm AWS site fully healthy. 15-minute observation window. All health checks green.
→
Phase 2
RESYNC
Re-enable AWS DMS replication. Sync data delta from on-prem back to Aurora. Monitor replication lag.
→
Phase 3
VALIDATE
Confirm replication lag < RPO threshold. Run automated smoke tests on AWS. Verify app functionality.
→
Phase 4
GRADUAL SHIFT
10% → monitor 5 min. 25% → monitor 5 min. 50% → monitor 10 min. 100% → complete.
→
Phase 5
CLEANUP
Disable failover-mode config. Reset Zerto replication direction. Update runbook documentation.
→
Phase 6
REVIEW
Post-incident review. Update RTO/RPO measurements. Improve runbook if gaps found.
⚠️ Failback is ALWAYS manual and gated. Never automate failback. Automated failback causes flip-flopping and can make outages worse.

Key Takeaways

Key Takeaways — Strategy 2: Active-Active Workload Partitioning

🔀

Both Sites Are Always Active

AWS and on-prem both serve live traffic simultaneously — for different app groups. Neither site is idle.

⚡

Failover = Scale-Up, Not Cold Start

Warm standbys run at reduced capacity at all times. On failure, they scale up to absorb 100% of traffic.

🔗

Always Layer Your Tools

Zerto/Veeam (compute) + AWS DMS (database) + Route53 (traffic) must all work together. No single tool covers all layers.

🗄️

DB Sync Is Separate from DR Tool

Zerto and Veeam handle VM replication. AWS DMS + Aurora Global DB handle database consistency. Both are required.

⚠️

Failback Must Be Manual

Never automate failback. Always use gradual traffic shifting (10%→25%→50%→100%) with monitoring at each step.

💰

Scope Zerto to Tier 0 Only

Use Zerto only for mission-critical Tier 0 workloads. Veeam handles Tier 1–3 at significantly lower cost — saving 60–80% on licensing.
